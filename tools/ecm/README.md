# ECM Wasm: первая попытка портирования под существующий сайт

Это исходники сборочного комплекта, а НЕ готовый или проверенный кодек.
Компиляция здесь не запускалась. Возможны ошибки upstream CMake, SIMD,
скрытых x86 intrinsics, отсутствующих скалярных реализаций, конфигураций,
внешних моделей и других зависимостей. Эти ошибки надо исправлять по логу,
а не считать workflow гарантированно работающим.

## Установка и запуск
1. Скопировать .github/workflows/build-ecm-wasm.yml и tools/ecm/ из архива
   в одноимённые места своего репозитория. Существующие файлы сайта не менять.
2. Сделать коммит. Workflow запускается только вручную:
   Actions -> Build ECM WebAssembly (experimental) -> Run workflow.
3. Дождаться результата. ecm-build-logs сохраняется и при ошибке.
4. Только при успешной сборке И smoke-тесте появится ecm-wasm-experimental.
   Он содержит js/ecm с Worker, модулями, сведениями о сборке и лицензией.
5. Перед публикацией отдельно проверить браузер и ограничения. Не копировать
   ecm-engine.js в сайт до получения модулей: существующая страница считает
   наличие этого файла признаком доступного движка.

## Сборка
Источник: официальный ECM, фиксированный тег ECM-20.0, не master.
Emscripten: 3.1.64 (выбранная воспроизводимая версия для первой попытки,
не заявление о том, что это новейшая или проверенная с ECM версия).
Точный commit и версия компилятора записываются в build-info.json.
Сборка без pthreads: каждый Worker использует один поток; существующая
страница может запускать несколько Worker. Поле threads пока не ускоряет
один экземпляр. HTML, токены и аппаратные ограничения не меняются.
Параметр max memory относится к одному модулю, а не ко всей вкладке.

Обрабатываются два известных места с arm64/x86 guards в CMake и семейство
ENABLE_SIMD_OPT в заголовках. Это не универсальный портировщик: если ECM
имеет другие безусловные intrinsics, сборка остановится, нужен новый патч.
Отключение NNLF interfaces не гарантирует отсутствие иных моделей/ресурсов.
Вшивается cfg целиком. Внешние модели автоматически не скачиваются.

## Протокол
encode сохраняет контракт js/danger.js: width/height/fps/qp/config,
frames как массив ArrayBuffer I420. config: ra, ld, ai.
Исходящие progress {done,total}, done {data}, error {message}.
Дополнительный log {message} существующая страница может игнорировать.
Прогресс берётся из строк POC; если логов нет, доступны только начало/конец.
Один Worker принимает ровно одно задание; остановка — terminate().

decode — программный API, не новый интерфейс:
  worker.postMessage({cmd:'decode', data:buffer}, [buffer]);
Ответ done содержит сырой YUV в выходном формате декодера, НЕ MP4 или RGBA.
Из параметров потока нужно отдельно получить размеры и разрядность;
данная версия API пока возвращает только байты и журнал.
Декодер не подключён к UI и сам по себе не наследует аппаратные проверки.
Не запускать его из нового интерфейса без тех же ограничений.

## Проверка и известные риски
Smoke тест кодирует один синтетический кадр 128x128 в AI, декодирует,
проверяет непустой поток и ожидаемый размер YUV при OutputBitDepth=8.
Он не сравнивает кодек с native-эталоном и не проверяет качество.
RA/LD, многосегментный поток и браузерный Worker этим не проверяются.
Если OutputBitDepth или другие CLI-флаги отличаются в исходниках, тест
должен завершиться ошибкой — исправляйте по реальному выводу.

В существующем danger.js сегменты кодируются независимо, затем байты
склеиваются. Работоспособность такого потока, сброс POC и вывод всех
кадров референсным декодером требуют отдельного теста. Нельзя считать это
подтверждённым способом сборки единого видео. Начинать проверку с 1 Worker.

Компиляция скачивает исходники в runner, не видео посетителя.
Результаты не коммитятся и не публикуются автоматически. Никаких secrets
или разрешений contents:write этому workflow не нужно.

Перед распространением изучите upstream лицензию и возможные патентные
условия. Комплект переносит найденные корневые license/COPYING файлы,
но это не заменяет юридическую проверку и аудит всех зависимостей.
